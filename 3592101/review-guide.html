02 / Reading strategy

Read by boundary,
not commit order.

Follow the data from Drupal to a component, then follow a request back. Use the questions to challenge the implementation.

  1. Contract → public APIDecide what must stay compatible before inspecting wiring.
  2. Providers → Drupal deliveryTrace null semantics, island identity, cacheability and import detection.
  3. Both Workbench pathsCompare mounted preview against generated entry output.
  4. Shared client → proxyReview transport, credentials, working copies and isolation together.
  5. Five frameworks → SSR prefetchCheck framework glue without moving secrets into rendering.
  6. Migration → evidenceReview fail-closed decisions; separate focused regressions from full application validation.
Review question

For each boundary: who owns the state, who may serialize it, and what happens when it is absent, stale or rejected?

03 / 01 / Contract & API

Move new hooks.
Do not move existing components.

The new entry point is deliberately narrow. There are no root aliases for the unreleased React additions.

Before · legacy getter

import { getPageData, Image } from 'drupal-canvas';

export default function Heading() {
  const page = getPageData();
  return <h1>{page.pageTitle}</h1>;
}

After · portable component

import { Image } from 'drupal-canvas'; // unchanged
import { usePageContext } from 'drupal-canvas/react';

export default function Heading() {
  const page = usePageContext();
  if (!page) return null; // author handles null
  return <h1>{page.pageTitle}</h1>;
}
Exact surface & compatibility decisions

Seven values: CanvasContextProvider, usePageContext, useSiteContext, useHasCanvasContext, JsonApiClientProvider, useJsonApiClient, useHasJsonApiClient.

Two types: CanvasContextProviderProps, JsonApiClientProviderProps. Neutral PageContext, SiteContext, CanvasContext and client types stay at the root.

Getters and the legacy JsonApiClient constructor still work in explicitly marked Drupal/Workbench runtimes. Elsewhere invocation throws migration guidance; importing alone does not. The runtime marker is not a security boundary.

Image, FormattedText, cn and menu/path helpers retain their paths; FormattedText still requires trusted/sanitized HTML. Region/RegionsProvider are deprecated, not relocated. Authoring utilities remain at drupal-canvas/json-render-utils.

The null guard above is an author choice, never synthesized by the codemod. Bare destructuring of a nullable getter result now leaves the whole file unchanged with manual guidance. An existing unconditional getPageData() ?? {} fallback can migrate.

Review question

Does each public path retain its intended identity and declaration contract? Do not confuse a dedicated /react entry with a React-free package root or a new RSC boundary.

04 / 02 / Runtime providers

Snapshot ownership,
not global current-page state.

Hooks synchronously read the nearest provider. They do not fetch context or create a client during every render.

Missing is meaningful

No provider or a null page/site yields null and a deduplicated warning. Empty assets or mainEntity: null inside a valid object are not missing context.

Precedence is explicit

An omitted renderer context inherits its parent. A supplied context replaces it—including explicit null values. No partial merge.

Clients are runtime objects

Integrations create/reuse clients. Page context never contains a client or token; replacing a provider client does not clear application SWR caches.

Integration-owned snapshot
→
Provider (no DOM wrapper)
→
Synchronous hook read
Older Content API responses: absent context is not fabricated context

The SDK already normalizes a successful response without context to { page: null, site: null }. A release-shaped Canvas 1.11 regression now follows that result through the shared React renderer: a null-safe consumer neither throws nor inherits unrelated outer context or turns the document head into page data.

This does not retrofit drupal-canvas/react into Drupal 1.11, make legacy getters legal in a headless runtime, or establish a full old-server round trip. Malformed present context and HTTP-error policy are separate concerns.

Review question

Can adjacent trees or concurrent requests accidentally share page data? Does a context update replace the snapshot while preserving component identity?

05 / 03 / Drupal delivery

Same routed entity.
Correct cache dependencies.

Trace the content response and each independent island separately. The default headless theme is an explicit selection, not request negotiation.

Headless context

The builder uses the rendered entity/translation for title and metadata; breadcrumbs, route, language and entity cacheability travel with the response.

Theme assets are populated

Headless selects system.theme:default. Core resolves logo/favicon URLs and MIME. Active-theme behavior remains for Drupal and Workbench.

Islands stay selective

Every island—including nested roots—gets providers. Import-based dependencies attach needed settings; settings-only AJAX updates notify mounted providers.

Cache and import-map review prompts
  • Check system.theme, core.extension, global/theme settings and rendered invalidation—including the first save of absent theme settings.
  • Empty favicon URL must not erase its configured MIME; file-content replacement is not configuration invalidation.
  • Follow the /react import-map entry through the Astro barrel and editor preview. Providers and consumers must share one Preact-compatible context instance.
  • Compare UI AST detection (named aliases and namespace members) with the PHP config-updater path. Preserve selective settings and separate inspection messages from data fetching.
  • Do not infer headless routing rewrites: Drupal-generated navigation URLs are retained.

Invariants worth comparing

Both paths use page defaults: pageTitle: '', breadcrumbs: [], mainEntity: null. There is no page-selection request. Site values and theme assets come from the same loaded data; legacy drupalSettings remain for old consumers.

Preserve upstream Brand Kit CSS in both paths. Dependency scanning covers the client, Workbench library and host components before serving, rather than hardcoding optional dependencies. Tests should cover published-package roots as well as source layouts.

07 / 05 / Framework-neutral client

Working copies before serialization.

One shared implementation owns revision reads and URL mapping. The proxy does not interpret JSON:API documents.

Resources & collections

Apply the session resource version unless explicitly selected. Collections fetch each item’s working copy, then serialize the merged raw document.

Failure classification matters

An ordinary item failure may retain the published item. Session rejection must propagate—not masquerade as an acceptable fallback.

Cache isolation is opt-in

Session-sensitive clients disable shared caching without a scope. Scoped keys also include resource version; application-owned caches remain the app’s responsibility.

Read the hard edges, not only getCollection()
  • Raw responses bypass working-copy transformations.
  • Keep locale, sparse fieldsets, includes and explicit resourceVersion on item reads; do not replay collection filter/sort/page parameters on them.
  • Deduplicate included resources so published copies cannot override selected primary working copies.
  • This does not discover every unpublished entity or filter/sort a collection by working-copy values. Accept the preview-only N+1 cost explicitly.
  • Check endpoint configuration precedence: an explicit full JSON:API URL overrides discovery; a configured/environment prefix is the fallback when discovery fails. Backend identity stays separate from the API override.
  • Check absolute pagination URLs, site subdirectories, full API overrides and path translation. Unknown mapped destinations must not bypass the boundary.

08 / 06 / Security boundary

The browser chooses a resource.
The server chooses credentials.

The framework-neutral handler accepts web Request/Response objects. Review credential handling and structural path restrictions separately: the matcher is not a Drupal-route authorization oracle.

Component → browser client
→
Same-origin application proxy
→
Configured Drupal endpoints

Session-driven auth

No preview session: unauthenticated. Valid session: server-held editor token. Invalid/expired session: error, never silent public fallback.

Constrained forwarding

Allowlisted headers; no browser authentication forwarded and no Drupal cookies returned. Paths and redirects stay on configured origins and installation roots, with the allowed endpoint structure.

Origin & cache rules

State changes require same-origin evidence. Draft responses are private, no-store; responses vary on Cookie. CORS alone is not CSRF protection.

Security questions to actively challenge
  • Trace encoded traversal, foreign URLs, localized paths and redirects through both mapping directions.
  • Does deployment sanitize forwarded host/proto headers used to establish the application origin?
  • Can a 401 from authenticated Drupal turn into a collection fallback? It must remain a session error; ordinary resource 403s are not session expiry.
  • Preview tokens retain ADR14’s view-only permission ceiling. Supporting HTTP methods does not grant draft mutation permission.
  • The proxy refuses unsupported PUT with 405. TanStack must actually route PUT to that handler.
  • The existing preview session uses HTTP-only, Secure, SameSite=None, Partitioned cookies. Neither page context nor runtime configuration contains the token.
  • ADR15 renewal remains. No automatic SWR cache clearing or new renewal protocol is introduced.
Custom language prefixes: structural matching, not membership

deutsch is valid prefix text; it need not be a language code. The mapper permits one safe segment immediately before the full configured JSON:API or router endpoint. Drupal core does not permit multi-segment language prefixes. Foreign API mounts require apiSiteUrl before a prefix can be placed at that site root.

No configured-language map is consulted. For example, a custom apiPrefix=api/v0 can structurally match /canvas/api/v0/auto-saves/pending, which is also a Canvas route. The matcher cannot certify Drupal route identity; Drupal access checks still matter. This is not an off-origin proxy or an installation-root escape.

Malformed/ambiguous escapes, dot segments, encoded separators, controls and URL delimiters are excluded as optional prefixes. Standard URL parsing may normalize a spelling before validation. Review the normalized destination, not a claim that every raw spelling is rejected.

09 / 07 / Framework glue

Five framework integrations.
No five-way policy fork.

Check route mounting and request/session bridging. Next.js and TanStack use the React renderer; Astro, Nuxt and Angular remain framework-native, not automatic hosts for React hooks.

Next.js

Route handlers delegate to the shared server. CanvasRuntime supplies nonsecret configuration; the template mounts the existing CSP middleware at its root. Neither CSP nor the native Angular runtime originated in this change.

TanStack Start

Loader/server integration supplies runtime configuration. Explicit PUT registration reaches the shared 405, rather than framework HTML fallback.

Astro

Integration injects the proxy route; ALL delegates through the request-aware draft server. The route is not prerendered. Environment forwarding includes CANVAS_JSONAPI_SITE_URL for foreign API installations.

Nuxt

The module registers a server route; H3 events become web requests. Session state follows the request, not a module-global user.

Angular

The upstream native integration retains page data in its store and TransferState. Its server handlers delegate to the shared SDK; adding the adapter does not turn Angular components into Drupal React code.

Review question

Do all adapters preserve method, body, status, cookies and proxy-path configuration? Are secrets confined to server/session code? Compare glue, not just README examples.

10 / 08 / SSR & prefetch

Two client instances.
Never one serialized client.

Server rendering is not automatic SWR prefetch. Meaningful initial HTML requires application-owned data fetching with matching fallback keys.

Draft renderer: no network

The renderer provides a non-null client, so SWR keys stay enabled. Draft fetch attempts during SSR throw ServerRenderingDraftFetchError with prefetch guidance.

Public renderer: unauthenticated

Public SSR uses a direct unauthenticated client. The browser uses the proxy. Neither rendering path receives serialized session credentials.

Hydration review prompts

Keep portable components synchronous. Next’s client boundary still permits initial server HTML; it does not make SWR fetchers server-only. Prefetch via the request-aware SDK before rendering; pass data, not client instances.

Verify fallback keys (use SWR unstable_serialize for compound keys), response shapes and initial preview state. Only serialize data this visitor may receive. DefaultSerializer’s non-enumerable getMeta()/getLinks() methods do not survive JSON hydration.

No automatic loader discovery, RSC conversion, or SWR cache-reset policy is introduced.

11 / 09 / CLI safety

Prove it is safe.
Otherwise leave the file alone.

Pull automatically migrates eligible getter calls only after both site and installed-package capability checks succeed.

Site: contextHooks === true
→
Installed /react: runtime hooks
→
Per-file safety → rewrite

Gate fails closed

Static export-graph analysis under import conditions; root-only, type-only, ambiguous or unverifiable exports do not qualify. No extra reactEntryPoint flag.

Rewrite is conservative

Resolve bindings/aliases and require unconditional, valid hook positions. Bare destructuring of a nullable result rejects the whole file with manual guidance. Existing left-hand nullish fallbacks can migrate; conditional branches cannot.

Respect author intent

Minimal import edits coalesce adjacent removals. Honor confirmation, --yes and --skip-overwrite. Report residual constructors even after successful getter conversion.

What does NOT get auto-migrated?

Client construction and helper modules get diagnostics only. Unrelated component/utility imports are not rewritten. This is not a generic root-to-/react import migration.

No null guard or non-null assertion is generated. const { pageTitle } = getPageData(); fails closed; const { pageTitle } = getPageData() ?? {}; can migrate. condition && getPageData(), right-hand nullish calls and conditional defaults remain blocked. This is not whole-program null-safety analysis.

Review shadowing, namespace use, React wrappers, early returns, callbacks, re-exports and identifier conflicts. Inspect the resulting syntax, not just the conversion count. Consolidated guidance belongs in terminal output, not component source.

13 / Review close

Approve contracts,
not a green badge.

Name the invariant you checked, the source you followed and the failure case you challenged.

  • Public surface: seven values/two provider prop types at /react; existing components, neutral types and authoring exports retain their paths.
  • Context: request/tree ownership, explicit-null precedence, independent islands and both Workbench outputs.
  • Drupal: rendered entity/language, default-theme assets without negotiation, cache invalidation and selective import detection.
  • Security: server-owned credentials, explicit session rejection, constrained origins/install roots and the documented structural-prefix tradeoff.
  • SSR: request-scoped prefetch and rendering clients stay separate; authorized data, not clients or secrets, crosses hydration.
  • Migration: capability gates, nullable destructuring refusal, unconditional fallbacks, binding safety, overwrite protection and residual-constructor guidance.
  • Compatibility: successful old responses with no context normalize to null slots; that does not supply missing module exports or deployable implementations to older Drupal releases.
Preserved upstream behavior is not a new ADR21 feature

Brand Kit, date helpers, CSP policy and the native Angular integration came from upstream. Review their preservation and integration, not their introduction as portable-runtime features. Date helper dependencies still use the active interface language; universal cross-frontend locale parity is not established.

The latest target change updates the SDC documentation example and image. It does not change the runtime contract. Full framework-application validation remains separate from focused package checks.

Explicitly outside this review

Workbench placeholder issue 3592114 ↗; automatic SWR cache resets; portable async Server Components; general component-import rewriting; a new push-time remote-runtime guard; malformed-context schema validation; changes to HTTP-error policy.

Unsupported PUT is intentionally rejected by the shared proxy and dispatched there by TanStack. Region APIs remain deprecated but compatible; no new region-provider integration is introduced.

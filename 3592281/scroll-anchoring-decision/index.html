Should the editor pane opt out of browser scroll anchoring?

The proposed fix is one CSS declaration, overflow-anchor: none on the editor pane. It removes the measured misalignment. The possible cost is losing a browser feature that keeps content still when something changes height. The editing, viewport, zoom and window scenarios tested on 2026-11-03 behaved the same before and after the fix, so that cost wasn't observed. Safari and Firefox weren't tested.

Decision: accepted on 2026-11-03. The limitations below still apply. Before and after videos are on the comparison page.

Measured observed in Chromium on the local site. Hypothetical reasoning, not observed. Untested could not be checked here.

Builds compared: before is 780a0520 (1.x, no overflow-anchor); with the fix is 9adbfb2f on the same base, with !1952 not included. Browser: Chrome for Testing 153 (Chromium), headless. Page-switch tests ran on 2026-11-02; scrolled-editing tests on 2026-11-03.

MeasuredWhy it happens

The editor frame centers the preview vertically. It resizes to fit the preview through a ResizeObserver, which runs one layout late. For that one layout, the preview sits off-center by half the height difference. Chromium's scroll anchoring then shifts the pane's scroll position to cancel the move. When the frame catches up and the preview moves back, Chromium skips the compensation, because the frame's resize cancels anchoring. The numbers below come from a recorded misaligned run.

Before: anchoring on
With the fix: anchoring off for the pane

The 8px case is the same mechanism with a 16px height change while the short page loads (768px ↔ 784px). Changing the preview height by 16px in the live editor moved the scroll by 8px with anchoring on, and not at all with it off. Whether a given switch misaligns depends on which element Chromium picks as its anchor. It is usually one of the editor's component outlines, which is why the bug is intermittent and more likely when the page's data is already cached.

MeasuredWhat opting out could cost, tested

Scroll anchoring exists to keep what is on screen still when content above it changes size. If the baseline preserved a visible position in these scenarios and the fix didn't, that would be the cost. Each scenario uses real editor controls on the demo Home page (5469px preview). The pane starts scrolled to 3147. Still untested

  • UntestedSafari and WebKit. Playwright's WebKit build downloaded but can't launch on this host, which lacks its system libraries (GTK 4, GStreamer). Installing them needs system package access. Support data (caniuse-lite 1.0.30001810) says released Safari and iOS Safari don't implement scroll anchoring, so they would ignore the setting and behave as before. That's inferred, not tested.
  • UntestedFirefox. It supports scroll anchoring (66+) but isn't installed here, so these scenarios ran in Chromium only.
  • HypotheticalOther content. These results cover the demo Home page and the review pages. The reasoning that the pane's anchoring can't look inside the preview iframe fits what was measured, but other component structures weren't tried.

Options

A. Opt the pane out of scroll anchoring (recommended)

overflow-anchor: none on .editorPane. Smallest change, and the only one that removes the measured misalignment in every run. Verified through browser comparisons; the configuration-only test was subsequently removed from the MR.

B. Stop centering the preview vertically

Align it to the top so a height change never moves it, leaving nothing for anchoring to compensate. It changes layout CSS, the same could still happen horizontally, and it hasn't been tried.

C. Re-align after every height change

Fight the shift with more scrolling. Adds timing logic and would override scrolling the user did on purpose. Not recommended.

Rejected: fit the frame before measuring

Tried first. Its unit tests passed, but the browser still misaligned 3/3, because the shift happens after measurement. Not part of the proposal.

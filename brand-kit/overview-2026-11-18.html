Canvas / Brand Kit

The Canvas Brand Kit as it works today

The Brand Kit is one set of fonts and colors for the whole site. Canvas turns it into a single stylesheet (@font-face rules plus :root CSS variables) and loads that stylesheet on the site's pages. Components can use the fonts by family name, and can use the colors as CSS variables or through color props. The Canvas CLI can copy the fonts and colors to a local canvas.brand-kit.json file and push them back.

Checked against Canvas 1.x at 6aeee189 on 2026-11-18. CLI commands and outputs were run with @drupal-canvas/cli@0.27.0, the version published from this tree. Statements are based on source, tests and CLI help. No Drupal site was run for this page.

1. What it is

The Brand Kit is stored in two kinds of config entity. Both are managed with the administer brand kit permission [1][3]. 

Drupal site
├── brand_kit.global       fonts[]: family, file URI, format, weight, style, axes
│                          only one per site: it can't be created or deleted over the API
└── color.<uuid> × n       name, cssVariable, value, displayFormat, weight
          │
          ▼  Canvas generates one stylesheet
@font-face { … }  for each font file
:root { --brand-primary: #0b5fff; … }  for each color
          │
          ▼  attached to every page rendered in the default (front-end) theme

Fonts are stored on the global brand kit. Each color is a color entity of its own. The brand kit still outputs the colors, because its CSS and API response include every color [2]. The CSS comes from BrandKit::getCss(): 

@font-face {
  font-family: 'Brand Sans';
  src: url('<public URL of the uploaded file>') format('woff2');
  font-weight: 400;
  font-style: normal;
  font-display: swap;
}

:root {
  --brand-primary: #0b5fff;
  --brand-ink: #101518;
}

Colors are ordered by weight, then by name. There are no CSS variables for fonts: the brand kit only defines the @font-face rules.

2. Fonts

Add fonts

In the Canvas editor, open Brand kit from the side menu and go to the Fonts tab. Accepted files are woff2, woff, ttf and otf [10]. You can also add fonts with canvas push from a local file or a provider (section 5).

Edit fonts

Rename or remove a family, remove a single variant, and set the weight and style of a static font. For a variable font, the axis ranges (for example wght 100–900) are saved. The axis slider positions are kept only in that browser.

Use in components

Refer to the family by name. The Fonts tab provides copyable snippets, generated by fontCss.ts [11]: 

/* global CSS (Tailwind 4) */
@theme {
  --font-brand-sans: "Brand Sans", sans-serif;
}
<p class="font-brand-sans">The quick brown fox jumps over the lazy dog.</p>

/* or plain CSS in a component */
.title { font-family: 'Brand Sans', sans-serif; }

3. Colors

A color has a name, a CSS variable, a value (sRGB or HSL, with an optional alpha) and a display format (hex, rgb or hsl) [1]. In the editor's Brand kit panel you can add, rename, find where a color is used, delete it, and organise colors into folders.

A color can't be deleted while a color prop points to it. The check looks at component instances in content (current and newer revisions), config such as templates and patterns, and auto-saves [4][19]. It doesn't look for the CSS variable in component CSS, global CSS or code.

Way 1: as a CSS variable

.card { background: var(--brand-primary); }

Canvas doesn't track this kind of use. If the color is deleted (in the UI or with canvas push --prune-colors), the variable disappears and this rule silently stops working. Search your CSS for the variable before deleting a color.

Way 2: as a color prop (the content editor picks the color)

# component.yml
props:
  type: object
  properties:
    background:
      type: string
      title: Background
      $ref: json-schema-definitions://canvas.module/color
      x-canvas-color-picker: kit-and-free   # default is kit-only
      # x-canvas-color-folders: [<folder uuid>]   # optional: limit the picker
      examples:
        - '#0b5fff'

The prop stores canvas-color:<uuid> for a brand kit color, or a literal #rrggbbaa / hsl() when a free color is allowed. At render time the string becomes the same object for React and Twig [5]: 

background = {
  value: { colorSpace: 'srgb', components: [0.0431, 0.3725, 1], hex: '#0b5fff' },  // abbreviated
  cssColorValue: 'rgb(11, 95, 255)',
  cssVariable: '--brand-primary',   // null for a free color
  colorName: 'Brand Primary',       // null for a free color
}
// React code component: cssColorValue works for brand kit and free colors
<div style={{ backgroundColor: background?.cssColorValue }} />

{# Twig / SDC #}
<div style="background-color: {{ background.cssColorValue }};"></div>

These example components come from the Canvas test modules [6]. Neither docs/code-component-metadata.md nor component-metadata.schema.json documents color props or the x-canvas-color-* keys yet.

4. Draft vs live: when a change reaches the site

The answer depends on what you change and where you change it.

Fonts, edited in the UI

Draft Saved as an auto-save on brand_kit/global. Editor previews show the change right away. The live site gets it only after it's published under Review changes [7]. If code components are published while a brand kit draft is unpublished, publishing fails until the brand kit is published too [8].

Colors, edited in the UI

Live Saved straight away with POST/PATCH/DELETE /canvas/api/v0/config/color. Each save rebuilds the live brand kit CSS. Colors have no draft step.

Fonts or colors, pushed with the CLI

Live canvas push writes to the live config directly. For fonts it sends PATCH /canvas/api/v0/config/brand_kit/global, which skips auto-save and Review [14].

Live pages

Get canvas/brand_kit.global, a static CSS file whose name contains a content hash. It's attached to every page rendered in the default theme, not only Canvas pages [9].

Editor previews

Get canvas/brand_kit.global.draft, served from /canvas/api/v0/auto-saves/css/brand_kit/global. This returns the draft if there is one, otherwise the saved version.

Code editor preview

Uses the published brand kit. It uses the font draft only when Canvas devMode is on.

Local Workbench

Reads only the colors in your local canvas.brand-kit.json, and reloads when the file changes. It doesn't load brand kit fonts or need a site connection [18].

5. The CLI today

The CLI is the npm package @drupal-canvas/cli, and its command is canvas. Two related packages are not the CLI: @drupal-canvas/workbench is the local preview, and @drupal-canvas/discovery is a shared library that contains the brand kit file parser. The CLI doesn't have a separate brand-kit command. Brand kit sync is part of pull and push, and it's on by default [12].

The file: canvas.brand-kit.json in the project root 

{
  "$schema": "https://unpkg.com/@drupal-canvas/workbench/dist/client/src/lib/schemas/brand-kit.schema.json",
  "fonts": {
    "families": [
      {
        "name": "Inter",
        "provider": "google",
        "weights": ["400", "700"],
        "styles": ["normal"]
      },
      {
        "name": "Brand Sans",
        "src": "fonts/Brand-Regular.woff2",
        "weights": ["400"],
        "styles": ["normal"]
      }
    ]
  },
  "colors": {
    "brand-primary": "#0b5fff",
    "brand-ink": "rgb(16, 21, 24)",
    "overlay": "hsla(220, 60%, 50%, 0.5)",
    "accent": {
      "value": "#f4c274",
      "name": "Warm accent",
      "displayFormat": "hsl"
    }
  }
}
  • Each color key becomes a CSS variable: brand-primary → --brand-primary. The display name defaults to the key in title case ("Brand Primary"). Accepted values are hex, rgb()/rgba() and hsl()/hsla(). Named colors such as rebeccapurple are rejected.
  • A font family comes from a local src file or from a provider: google, bunny, fontshare, fontsource, npm or adobe.
  • If a top-level key is missing, the CLI leaves that part of the site alone. An empty "families": [] is different: it clears every font on the site [15].

Commands, by what they change

# Check the file. Offline, changes nothing.
npx canvas validate

Read-only The example file above passes. A file with mistakes produces errors like these (output from a real run, shortened): 

✗ canvas.brand-kit.json
  Color "--brand-primary": duplicate of "brand-primary" — both name the CSS variable "--brand-primary".
  Color "bad": invalid value "rgb(300, 0, 0)". Expected a CSS color string like "#cc0000", …
  Color "named": invalid value "rebeccapurple". …
  Font family "Missing" (index 0): file not found: fonts/nope.woff2
# Copy the site's brand kit into local files (asks for confirmation; -y skips it)
npx canvas pull

Writes local files This creates canvas.brand-kit.json if it doesn't exist. It downloads font files into fonts/ and adds them as local src entries, so a Google font comes back as files. It merges colors in and leaves entries that are already the same untouched. It also rewrites color examples in component.yml from canvas-color:<uuid> to canvas-color:<key> [13]. As usual, pull also pulls components, global CSS, pages and templates. 

# Send local fonts and colors to the site (shows a plan, then asks for confirmation)
npx canvas push

Writes the live site If the file has fonts, the site's font list is replaced with the file's. If it has colors, colors are created or updated, matched by CSS variable. Site colors that aren't in the file are reported but kept. A canvas-color:<key> in local components or pages is converted back to the color's UUID. The same command also pushes every local component, the global CSS, pages and templates. There's no option to push only the brand kit.

Push can delete other things from the site. This doesn't depend on --prune-colors [20]:

  • Code components: if the project has at least one local component, every code component on the site that isn't in the project is deleted. External (headless) components are never deleted.
  • Page templates: while page-template sync is on (the default), every page template on the site that isn't in the local page templates folder is deleted. This applies even when that folder is empty. The site's current default template is kept unless another template becomes the default.

To check before anything changes, run canvas push without -y. Look for delete rows in the Plan table and answer "no". Before that prompt the CLI only sends read requests. To keep page templates out of the push, add --no-page-templates. 

# Also delete site colors that aren't in the file.
# Colors used by a color prop are refused; colors used only through var(--…) in CSS are not protected.
npx canvas push --prune-colors

# Leave the brand kit out of a sync
npx canvas pull --no-include-brand-kit
npx canvas push --no-include-brand-kit     # or CANVAS_INCLUDE_BRAND_KIT=false

npx canvas needs the CLI installed in the project. To run the exact version used for this page, use npx @drupal-canvas/cli@0.27.0 validate. When brand kit sync is on, the CLI requests the OAuth scope canvas:brand_kit. That scope maps to administer brand kit, which covers fonts, colors and font uploads [16].

6. Limits, gaps and open questions

  • Only one kit per site. Everything uses global. I found no planned work for more than one brand kit.
  • Color order: the UI can't reorder colors (new colors get weight 0). canvas push changes weights so the site order follows the order of keys in the file.
  • Folders are managed only in the UI. Colors created by push land at the top level, and the CLI doesn't apply a prop's folder restriction.
  • Color spaces: only sRGB and HSL. Per-space range validation is still a @todo in the schema.
  • Variable fonts: the generated @font-face has no variation settings, and slider positions aren't saved.
  • Docs are behind the code. The user guide brand-kit.mdx covers only font sync and calls it opt-in, but sync is on by default and includes colors [17]. docs/config-management.md says the brand kit holds design tokens, but colors are separate entities. The CLI README says brand kit sync applies "when canvas.brand-kit.json is present", but pull runs without the file and creates it.
  • Not checked: what happens when canvas push changes fonts while a UI font draft is still unpublished. Canvas records each draft's original hash for conflict detection, but I didn't run this case.
